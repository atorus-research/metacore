================================================================================
ANALYSIS: Creating CDISC Define.xml 2.0 from P21 ADaM Specification via Metacore
================================================================================

Date: 2026-05-31
Document: Gap Analysis for Define.xml Generation from Metacore Objects

================================================================================
EXECUTIVE SUMMARY
================================================================================

A complete Define.xml 2.0 generation capability from metacore objects is
CURRENTLY NOT IMPLEMENTED. While metacore can READ Define.xml files (via the
define_to_metacore() function), it CANNOT WRITE Define.xml files from metacore
objects.

The good news: The metacore data model captures most critical information needed
for Define.xml generation. However, several important pieces of Define.xml-specific
metadata are either:
  1. Missing entirely from the metacore model
  2. Stored but not properly structured for XML generation
  3. Would require significant new functionality

This analysis identifies the gaps and provides a roadmap for implementation.

================================================================================
1. CURRENT STATE: WHAT METACORE CAN DO
================================================================================

1.1 XML Reading (Currently Implemented)
--------------------------------------
The metacore package has the following XML→metacore reading capabilities:
  • define_to_metacore(path): Main entry point to read Define.xml 2.0
  • xml_to_ds_spec(): Extract dataset specs (dataset name, structure, label)
  • xml_to_ds_vars(): Extract dataset-variable associations with key sequences
  • xml_to_var_spec(): Extract variable metadata (type, length, label, format)
  • xml_to_value_spec(): Extract value-level metadata including where clauses
  • xml_to_codelist(): Extract codelists, permitted values, external libraries
  • xml_to_derivations(): Extract methods/MethodDef and comments/CommentDef

This bidirectional reading capability is critical - it shows metacore CAN handle
Define.xml complexity on the input side.

1.2 Metacore Data Model
-----------------------
The metacore object currently stores 7 tables:
  1. ds_spec: dataset name, structure label
  2. ds_vars: dataset, variable, key_seq, order, mandatory, core, supp_flag
  3. var_spec: variable, type, length, label, common, format
  4. value_spec: dataset, variable, type, origin, sig_dig, code_id,
                 where, derivation_id
  5. derivations: derivation_id, derivation text
  6. codelist: code_id, name, code table, type
  7. supp: dataset, variable, idvar, qeval

This model captures the CORE metadata for Define.xml generation.

================================================================================
2. DEFINE.XML 2.0 STRUCTURE OVERVIEW
================================================================================

The CDISC Define.xml 2.0 format (ODM 1.3.2 with def: namespace) requires:

2.1 High-Level XML Structure
----------------------------
<?xml version="1.0"?>
  <ODM> (with namespaces, file metadata)
    <Study OID>
      <GlobalVariables>
        <StudyName>
        <StudyDescription>
        <ProtocolName>
      </GlobalVariables>
      <MetaDataVersion> (with DefineVersion, StandardName, StandardVersion)

        <!-- Define.xml Extensions -->
        <def:AnnotatedCRF>
        <def:ValueListDef> (defines where clauses)
        <def:WhereClauseDef> (defines value-level conditions)

        <!-- Standard ODM Definitions -->
        <ItemGroupDef> (one per dataset)
          <Description>
          <ItemRef> (one per variable)
            <def:WhereClauseRef> (references value-level conditions)
        <ItemDef> (one per unique variable)
          <Description>
          <def:Origin> (with Type, PDFPageRef, etc.)
          <CodeListRef>
          (other attributes)
        <CodeList> (one per codelist)
        <ExternalCodeList>
        <MethodDef> (one per method/derivation)
        <def:CommentDef> (one per comment)

2.2 Key XML Attributes and Elements
------------------------------------
OID (Object Identifiers): All elements need unique OIDs following conventions:
  • ItemGroupDef: "IG.{domain}"
  • ItemDef: "IT.{domain}.{variable}" or "IT.{domain}.{var}.{dataset}.{var}.EQ.{hash}"
  • CodeList: "CL.{codelist_id}" or specific format
  • MethodDef: "MT.{domain}.{variable}" or custom
  • WhereClauseDef: "WC.{domain}.{variable}.{condition}"

Mandatory Attributes by Element:
  • ODM: ODMVersion, FileType, FileOID, CreationDateTime, SourceSystem
  • Study: OID
  • MetaDataVersion: OID, Name, DefineVersion, StandardName, StandardVersion
  • ItemGroupDef: OID, Name, Repeating, IsReferenceData, Purpose, def:Structure,
                  def:Class, SASDatasetName
  • ItemRef: ItemOID, OrderNumber, Mandatory, (KeySequence when applicable)
  • ItemDef: OID, Name, DataType, Length (for character), SASFieldName
  • def:Origin: Type (Collected, Derived, Assigned, Predecessor), Page references
  • CodeList: OID, Name, Preference (for codelist type)

3. P21 SPECIFICATION STRUCTURE
================================================================================

The vlm_test_spec.xlsx file contains 9 sheets with the following structure:

3.1 Define Sheet
----------------
Attributes: StudyName, StudyDescription, ProtocolName, Language, Standards, etc.
Purpose: Global-level metadata for the Define.xml root elements

3.2 Datasets Sheet
------------------
Columns: Dataset, Label, Class, Structure, Key Variables, Repeating,
         Reference Data, Comment, Developer Notes
Purpose: Dataset-level metadata → ItemGroupDef elements

3.3 Variables Sheet
-------------------
Columns: Order, Dataset, Variable, Label, Data Type, Length, Significant Digits,
         Format, Mandatory, Assigned Value, Codelist, Common, Origin, Pages,
         Method, Predecessor, Role, Comment, Developer Notes
Purpose: Variable-level metadata → ItemDef + ItemRef elements

3.4 ValueLevel Sheet
--------------------
Columns: Order, Dataset, Variable, Where Clause, Label, Data Type, Length,
         Significant Digits, Format, Mandatory, Assigned Value, Codelist,
         Origin, Pages, Method, Predecessor, Comment, Developer Notes
Purpose: Value-level conditions → def:WhereClauseDef + def:ValueListDef

3.5 Codelists Sheet
-------------------
Columns: ID, Name, NCI Codelist Code, Data Type, Order, Term, NCI Term Code,
         Decoded Value
Purpose: Code/decode pairs → CodeList elements

3.6 Dictionaries Sheet
----------------------
Columns: ID, Name, Data Type, Dictionary, Version
Purpose: External reference libraries → ExternalCodeList elements

3.7 Methods Sheet
-----------------
Columns: ID, Name, Type, Description, Expression Context, Expression Code,
         Document, Pages
Purpose: Derivation/computation methods → MethodDef elements

3.8 Comments Sheet
------------------
Columns: ID, Description, Document, Pages
Purpose: Comments on variables → CommentDef elements (def: namespace)

3.9 Documents Sheet
-------------------
Columns: ID, Title, Href
Purpose: Document references for PDFs → def:DocumentRef + def:leaf elements

4. MAPPING: P21 SPECIFICATION → DEFINE.XML → METACORE
================================================================================

4.1 Successful Mappings (Currently Captured by Metacore)
-------------------------------------------------------

P21 Datasets → Metacore ds_spec:
  • Dataset → dataset
  • Label → label
  • Structure → structure
  • Class → (NOT CAPTURED - see Gap #1)
  • Repeating → (NOT CAPTURED - see Gap #2)

P21 Variables → Metacore ds_vars + var_spec:
  • Variable → variable
  • Label → label (in var_spec)
  • Data Type → type (in var_spec)
  • Length → length (in var_spec)
  • Mandatory → mandatory (in ds_vars)
  • Order → order (in ds_vars)
  • Codelist → code_id (in value_spec)
  • Common → common (in var_spec)
  • Origin → origin (in value_spec)
  • Method → derivation_id (in value_spec/ds_vars)
  • Significant Digits → sig_dig (in value_spec)
  • Format → format (in var_spec)

P21 ValueLevel → Metacore value_spec:
  • Where Clause → where (in value_spec)
  • Label → (PARTIALLY - only at variable level, not value level)
  • Method → derivation_id (in value_spec)
  • Origin → origin (in value_spec)

P21 Codelists → Metacore codelist:
  • ID → code_id
  • Name → names
  • Term/Decoded Value → codes (nested tibble)
  • Type → type (code_decode vs permitted_val)

P21 Methods → Metacore derivations:
  • ID → derivation_id
  • Name → (NOT CAPTURED - see Gap #3)
  • Description → derivation (text)
  • Type → (NOT CAPTURED - see Gap #4)
  • Document → (NOT CAPTURED - see Gap #10, linked implicitly through method)
  • Pages → (NOT CAPTURED - see Gap #10, linked implicitly through method)

P21 Documents → Metacore study_level or new documents table:
  • ID → (reference key for linkage from Methods sheet)
  • Title → (document title/description)
  • Href → (file reference, e.g., "adrg.pdf")

P21 Comments → Metacore derivations:
  • ID → derivation_id
  • Description → derivation (text)

4.1.1 P21 Implicit Document Linking Pattern
---------------------------------------------

In the P21 standard, page references and document links are defined IMPLICITLY
through the Methods sheet, NOT through direct columns in Variables/ValueLevel:

P21 Specification Structure:
  Variables Sheet:        Variable references a Method ID (e.g., "ADEX.AVAL_CALC")
  ↓ (via Method column)
  Methods Sheet:          Method has Document ID and Pages (e.g., "adrg" and "45-47")
  ↓ (via Document column)
  Documents Sheet:        Document ID maps to actual file and title

Example mapping:
  Step 1: Variables sheet row
    Dataset=ADEX, Variable=AVAL, Origin=Derived, Method=ADEX.AVAL_CALC

  Step 2: Methods sheet row (referenced by Method ID)
    ID=ADEX.AVAL_CALC, Document=adrg, Pages=45-47

  Step 3: Documents sheet row (referenced by Document ID)
    ID=adrg, Title=Analysis Data Reviewer's Guide, Href=adrg.pdf

  Final Define.xml result:
    <ItemDef OID="IT.ADEX.AVAL">
      <def:Origin Type="Derived">
        <def:DocumentRef leafID="adrg">
          <def:PDFPageRef PageRefs="45-47"/>
        </def:DocumentRef>
      </def:Origin>
    </ItemDef>

This implicit pattern is why:
  • Value_spec does NOT need page_refs
  • Derivations table MUST be extended with document_id and pages
  • A documents table (or equivalent) must be added to metacore

4.2 Problematic Mappings (Requires Schema Changes)
--------------------------------------------------

The following P21 specification metadata CANNOT be stored in current metacore:

  Gap #1: Dataset Class (e.g., "SPECIAL PURPOSE", "INTERVENTIONS")
    - P21 Location: Datasets sheet, "Class" column
    - Define.xml: ItemGroupDef@def:Class attribute
    - Issue: No field in ds_spec for classification
    - Impact: Generated Define.xml will lack domain classification

  Gap #2: Dataset Repeating & IsReferenceData flags
    - P21 Location: Datasets sheet, "Repeating" and "Reference Data" columns
    - Define.xml: ItemGroupDef@Repeating and @IsReferenceData attributes
    - Issue: No fields in ds_spec for these boolean flags
    - Impact: Generated Define.xml will lack repeating/reference metadata

  Gap #3: Method Name (distinct from derivation description)
    - P21 Location: Methods sheet, "Name" column
    - Define.xml: MethodDef@Name attribute (required)
    - Issue: Metacore only stores derivation_id and derivation (description)
    - Impact: Cannot generate proper MethodDef@Name; would need to reconstruct
              from the ID or description

  Gap #4: Method Type (Computation, Predecessor, Assigned, Imputation)
    - P21 Location: Methods sheet, "Type" column
    - Define.xml: MethodDef@Type attribute
    - Issue: No field in derivations table for method type
    - Impact: Cannot generate Define.xml with correct MethodDef@Type;
              can only infer from context (e.g., origin field)

  Gap #5: Variable Role (IDENTIFIER, TOPIC, VARIABLE QUALIFIER, etc.)
    - P21 Location: Variables sheet, "Role" column
    - Define.xml: ItemRef@Role attribute
    - Issue: No field in ds_vars for role classification
    - Impact: Generated Define.xml will lack variable role information
    - Severity: MEDIUM - useful but not critical for Define generation

  Gap #6: NCI Codelist Code Reference
    - P21 Location: Codelists sheet, "NCI Codelist Code" column
    - Define.xml: CodeList@Preference attribute (for NCI references)
    - Issue: Metacore codelist only stores code_id, name, codes, type
    - Impact: Cannot generate CodeList@Preference pointing to NCI
    - Severity: LOW - needed for advanced functionality

  Gap #7: Value-Level Labels (distinct from variable labels)
    - P21 Location: ValueLevel sheet, "Label" column (per where clause)
    - Define.xml: def:WhereClauseDef can have associated descriptions
    - Issue: value_spec stores where clause text but not where label
    - Impact: Value-level documentation lost in Where Clause
    - Severity: MEDIUM - useful for complex value documentation

  Gap #8: SASDatasetName vs Dataset Name
    - P21 Location: Variables sheet and Datasets sheet (implicit)
    - Define.xml: Multiple attributes (@SASDatasetName, @Name, etc.)
    - Issue: Metacore may not preserve the exact SAS dataset name format
    - Impact: May affect XPT file naming in output
    - Severity: LOW - usually matches domain name

  Gap #9: Expression Context and Expression Code (for methods)
    - P21 Location: Methods sheet columns
    - Define.xml: Can appear in MethodDef description or as extended content
    - Issue: Metacore derivations only store text description
    - Impact: Cannot preserve formal expression/code syntax
    - Severity: LOW - mostly informational

  Gap #10: Page References and Document Links (via Methods)
    - P21 Location: Methods sheet "Document" and "Pages" columns
    - Define.xml: def:Origin/def:DocumentRef/def:PDFPageRef
    - P21 Pattern: IMPLICIT - Variable → Method → Document + Pages
      Method links to Document (by ID), and Methods sheet contains Pages
    - Issue: Metacore derivations table doesn't store document_ref or pages
    - Impact: Cannot generate linked document references in Define.xml
    - Severity: MEDIUM - important for traceability and regulatory compliance
    - Note: Document linking is implicit through the method relationship, not
            through a separate column in Variables/ValueLevel sheets

  Gap #11: Study-Level Metadata (from Define sheet)
    - P21 Location: Define sheet (StudyName, StudyDescription, etc.)
    - Define.xml: ODM/@FileOID, Study/@OID, GlobalVariables elements
    - Issue: Metacore has no place to store study-level metadata
    - Impact: Cannot auto-generate ODM structure without user input
    - Severity: HIGH - critical for valid Define.xml

  Gap #12: KeySequence for Variables
    - P21 Location: Variables sheet (implicit key variables)
    - Define.xml: ItemRef@KeySequence (ordering for compound keys)
    - Mapping: PARTIAL - ds_vars has key_seq, but must be properly ordered
    - Impact: Can be derived from ds_vars.key_seq if properly populated
    - Severity: LOW (already captured, but verification needed)

5. ADDITIONAL XML GENERATION REQUIREMENTS
================================================================================

5.1 OID Generation Strategy
---------------------------
Define.xml requires consistent, deterministic OID generation. Current strategy
in metacore readers:

  For simple ItemDef: "IT.{DOMAIN}.{VARIABLE}"
  For value-list ItemDef: "IT.{DOMAIN}.{VARIABLE}.{DATASET}.{VAR}.EQ.{HASH}"
    where HASH is a unique identifier for the where clause

Issues for generation:
  • Need deterministic hash algorithm for where clauses
  • Must ensure OID uniqueness across all elements
  • Should match conventions if recreating existing files

5.2 CreationDateTime
--------------------
Define.xml@CreationDateTime is required (ISO 8601 format with timezone).
Metacore has no storage for this.
Impact: Would need to generate dynamically or accept as parameter.

5.3 SourceSystem Identification
-------------------------------
Define.xml@SourceSystem and @SourceSystemVersion identify the creating software.
Currently Pinnacle 21 shows "Pinnacle 21 Community" and "3.1.0".
If generating from metacore, should indicate "R metacore package" and version.

5.4 XSL Stylesheet Reference
-----------------------------
Define.xml includes: <?xml-stylesheet type="text/xsl" href="define2-0-0.xsl"?>
Need to determine if/where to store stylesheet location.

5.5 Namespace Handling
---------------------
Define.xml uses multiple namespaces:
  • xmlns="http://www.cdisc.org/ns/odm/v1.3"
  • xmlns:def="http://www.cdisc.org/ns/def/v2.0"
  • xmlns:xlink="http://www.w3.org/1999/xlink"
  • xml:lang="en" (on text elements)

Must be preserved in generation.

5.6 Archive Location References (def:ArchiveLocationID)
-------------------------------------------------------
ItemGroupDef@def:ArchiveLocationID points to the XPT file location.
Example: def:ArchiveLocationID="LF.ADEX"
This requires knowledge of which leaf files exist.

   derivations table. This created an unhandled edge case: a variable cannot
   have BOTH a derivation (MethodDef) AND a comment (CommentDef) because
   derivation_id maps to one or the other.

   New design:
     • Separates comments into their own table (clean single responsibility)
     • Links via value_spec.comment_id (enables per-dataset variability)
     • Allows variables to have both a method AND a comment independently
     • More extensible for future comment metadata (title, source, etc.)
